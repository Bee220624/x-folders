## 一句话结论

**底子是好的，大部分保留。** 数据层、消息层、帖子识别和按钮注入写得扎实，而且吸收了真实 X 页面的实测结论。问题集中在三处：

1. **从没在真实浏览器里装上过**：构建产物放在隐藏目录，你选错了文件夹（已在工单里改为 `dist/`）；
2. **插件界面的按键会漏给 X**，打字时会触发 X 的快捷键——很可能是「把 X 页面搞坏了」的来源之一（见缺陷 1）；
3. **界面是按「只在页面内、只显示文字」写的**：新工单的富卡片、搜索、侧边栏模式，需要把阅读界面抽成两种模式共用的组件。

## 一、审查中发现的缺陷

| # | 严重度 | 问题 | 证据 | 处理 |
|---|---|---|---|---|
| 1 | **高** | **按键外泄，触发 X 快捷键。** 插件所有输入框（新建 / 重命名文件夹、弹层里新建文件夹）只拦截了 Esc，其余按键全部传给 X。插件界面在封闭的 Shadow DOM 里，X 在页面层面看到的按键来源和当前焦点都是一个普通 `div`，而不是输入框，因此很可能把字母当快捷键执行（例如 N 发帖、R 回复、T 转帖、J/K 切换帖子）。在文件夹名里打一个「Prompt」就可能连着触发回复和转帖。（由读代码推断，第 1 步真机确认） | `InlineNameEditor.tsx:59-69` 只处理 Enter / Escape；全仓库没有任何通用的按键拦截（已搜索 `stopPropagation` / `keydown`） | 在每个插件宿主上统一拦截键盘事件，不让它们传到 X（工单 3.3 第 3 条），并加端到端测试 |
| 2 | 中 | **高频全量重扫。** X 页面任何变化（时间线本来就在不停变）停下来约 0.12 秒后，都会把页面上所有帖子重新提取一遍、重新检查按钮，并重新测量左栏布局。这违背了它自己「不在页面变化时全页扫描」的规则，可能拖慢滚动 | `XRuntime.ts:142-153` 根观察器 → `#ensureAll()` → `scanTweetRoots(document)`（第 139 行）+ `sidebar.ensure()` | 根观察器只负责左栏和主栏「整体被替换」的情况；帖子只走增量检测（已有 `TweetDetector` + `MutationBatcher`） |
| 3 | 低 | 后台自报的版本号写死为 `0.1.0` | `handlers.ts:27` | 改为读取清单里的版本号 |
| 4 | 低 | 文件夹树的深度值和「子孙」计算写死为两层；目前两层下结果正确，但和工单「不写死两层」的要求不一致 | `folder.ts:41-46`、`FolderRepository.ts:140-147` | 改为递归计算 |
| 5 | 低 | 文档里说「页面脚本改写 `attachShadow` 就能拿到插件的 closed Shadow Root」。在 Chrome 里内容脚本运行在独立的隔离环境，页面改不到它的原型链，这个说法不成立 | `ShadowHost.ts:43-47` 等处注释 | 更正注释和文档，不影响功能 |
| 6 | 待真机验证 | 左栏文件夹树、窄屏弹出面板、右键菜单都是挂在 X 左栏里的固定定位元素，可能被 X 的层叠关系盖住或裁切 | `SidebarApp.tsx`、`FolderContextMenu.tsx` | 第 1 步真机验证时重点看 |

另外一个需要知道的设计事实（不是缺陷）：收藏列表里的卡片是普通链接，点开会**整页重新加载** X（约 1–2 秒），不是 X 内部的快速跳转。新工单的「返回恢复」已经按「可能整页加载」来设计。

## 六、对执行顺序的建议

工单第 5 节第 1 步「最小闭环」里，顺带先修两件事：

1. **缺陷 1（按键外泄）**：它直接影响「会不会把 X 页面搞坏」，修复代价小；
2. **缺陷 2（高频全量重扫）**：它影响滚动流畅度，放在最小闭环里一起用真机检查。

其余修改按工单第 5 节第 2 步的顺序进行。
